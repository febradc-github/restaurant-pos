# C-25: Inventory Threshold & Restock API -- Design

## Parent
Part of [[EP-23]] -- see [[DS-23]] for the umbrella rationale.

## Problem
`InventoryItem` only tracks raw stock ([[EP-1]]/C-5) -- there's no concept of how much of an ingredient is needed to get through one more day of service, and no way for the Owner to see what to buy before tomorrow.

## Approach
Add a `threshold` column to `InventoryItem` (nullable/default 0, Owner-overridable). Add an Owner-gated endpoint that computes, per ingredient, a suggested threshold from the trailing 30 days of Paid-order consumption: sum each ingredient's `quantity_required` (via the `menu_item_inventory_item` pivot) across every `OrderItem` on a `Paid` order within that window, divided by 30 for an average daily usage figure. An ingredient with no Paid-order history in that window gets a suggested threshold of 0. A separate (or combined) endpoint returns the live restock view: current stock, threshold, and shortfall (`max(0, threshold - stock)`) per ingredient. Add an update endpoint for the Owner to override a threshold directly.

## Acceptance criteria
- `threshold` column exists on `inventory_items`, defaulting to 0.
- An endpoint computes a suggested threshold per ingredient from the trailing 30 days of Paid-order consumption (average daily usage), returning 0 for an ingredient with no history in that window.
- A live endpoint returns, per ingredient, current stock, threshold, and shortfall (quantity needed to reach threshold, 0 if at or above it) -- computed on each request, no stored snapshot or scheduled job.
- Owner-gated endpoint lets the Owner override an ingredient's threshold directly.
- All endpoints are Owner-gated (`auth:sanctum` + `role:owner`).
- Covered by tests including a real mutation/query check of the 30-day windowing (orders inside vs. outside the window) and the no-history-yet zero-threshold case.
