# C-12: Kitchen PIN Clock-In/Out -- Design

## Parent
Part of [[EP-10]] -- see [[DS-10]] for the umbrella rationale.

## Problem
Kitchen staff share one device and must keep the order display ([[src-app-tsx]] kitchen route) public and gate-free -- that constraint from [[AR-POS-core]] is preserved deliberately. But they still need a way to record attendance without full per-person login slowing down or blocking that shared screen.

## Approach
Give Kitchen staff real `UserRole::Kitchen` User records, each with a unique 6-digit PIN (unique among active Kitchen staff). Add a separate, lightweight PIN endpoint -- distinct from Sanctum login, issuing no session token -- that accepts a PIN, resolves it to a Kitchen user, and creates a `time_entries` row (`clock_in = now()`) if the user has no open entry, or closes their open entry (`clock_out = now()`) if one exists. On the frontend, add a PIN-pad overlay on the Kitchen display screen for clock-in/out; it operates independently of and does not block or gate the live order view underneath it.

## Acceptance criteria
- Kitchen `User` records exist (`UserRole::Kitchen`) each with a unique 6-digit PIN.
- A PIN-based endpoint (no `auth:sanctum`, no token issued) accepts a PIN and either opens a new `time_entries` row for the matching Kitchen user (if none open) or closes their open one, toggling clock-in/clock-out on each submission.
- An invalid or unrecognized PIN is rejected with a generic error, without revealing which PINs exist or are valid.
- The Kitchen order display continues to load and receive live updates with no login required, unchanged from its current behavior (explicit regression check against [[AR-POS-core]]'s no-login constraint).
- A PIN-pad overlay is present on the Kitchen display screen; entering a valid PIN clocks the matching employee in or out and shows a brief confirmation, without navigating away from or interrupting the live order view.
