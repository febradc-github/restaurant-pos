# C-20: Owner Employee Management -- Design

## Problem

There is currently no production path to create a `User` in this system. `UserRole` (Owner/Cashier/Server/Kitchen), the `User` model, and the `pin` column (added for Kitchen in [[EP-10]]/C-12) already exist, but every `User` in the codebase so far exists only via database factories used in tests -- `OwnerController` is still just a stub dashboard endpoint. Without real employee registration, C-10's entire attendance system (C-11 Server/Cashier login-based clock, C-12 Kitchen PIN clock-in) has no way to onboard actual restaurant staff.

## Architecture

Builds on [[EP-10]] (Attendance & Extended RBAC) and lands its UI inside [[EP-14]]'s OwnerPage nav shell, which [[DS-16]] explicitly designed to accept more sections ("Employee Management ... land here as later epics without restructuring this shell") without restructuring.

- **Backend**: new Owner-gated (`auth:sanctum` + `role:owner`) endpoints reusing the existing `User` model and `UserRole` enum. No new tables -- adds one `active` boolean column to `users` (default `true`).
- **Auth integration**: [[EP-10]]'s existing gates (`AuthController::login` for Owner/Cashier/Server, `KitchenClockController::clock` for Kitchen) are extended to also check `active`, rejecting a deactivated employee at the same point they already reject a wrong role/credential -- no new gating mechanism introduced.
- **Frontend**: a new "Employees" entry in `OwnerPage`'s `NAV_ENTRIES` array ([[DS-16]]), a new nested route (e.g. `/owner/employees`), consistent with the `/owner/tables` and `/owner/menu` pattern already established.

## Approach

1. Migration: add `active` boolean to `users`, default `true`.
2. Backend `EmployeeController` (Owner-only): `index` (list all employees with role/active status), `store` (create -- name, role, and role-appropriate credential: password for Owner/Cashier/Server, unique 6-digit PIN for Kitchen), `update` (change role and/or reset credential), `deactivate`/`reactivate` (toggle `active`, blocking self-deactivation and deactivating the last active Owner).
3. Extend `AuthController::login` and `KitchenClockController::clock` to reject when the resolved user's `active` is `false`, using the same generic-rejection style already established (no distinguishing information leaked about why).
4. Frontend: `EmployeesPage`-equivalent section (`Table` of employees with role/active status, an "Add Employee" `Form` with role-conditional fields per the brainstormed shape, deactivate/reactivate actions, role/credential edit) added to `OwnerPage`'s nav and content area, styled consistently with [[DS-16]]'s established patterns (Card + Table + Form).

Split into two stories at breakdown: backend CRUD API first, Owner-facing UI second (consumes the API).

## Trade-offs considered

- **Hard delete instead of deactivate** -- rejected. Would orphan or cascade-delete historical `time_entries`/`orders` rows referencing that `user_id`, destroying attendance and order history. Deactivate preserves all history while blocking future login/clock-in.
- **System-generated temp password with delivery** -- rejected for v1; no email/SMS delivery infrastructure exists in this project, and this is a single-location restaurant where the Owner can set/relay credentials directly. Owner sets the password (or PIN) directly at creation and can reset it later.
- **No self-lockout guard** -- rejected. Blocking self-deactivation and last-Owner deactivation is cheap to implement and prevents an unrecoverable state (nobody left who can log in to fix it).
- **One combined backend+frontend story** (matching C-3/C-4/C-6/C-7's pattern) -- considered, but a two-story split (API, then UI) was chosen instead, closer to how C-15/C-16 in the C-14 epic separated foundation-layer work from page-layer work.

## Acceptance criteria

- Owner can create a new employee (name + role + role-appropriate credential: password for Owner/Cashier/Server, unique 6-digit PIN for Kitchen) through the app, with no direct database/factory access required.
- Owner can view a list of all employees with their role and active/inactive status.
- Owner can change an existing employee's role and reset their credential.
- Owner can deactivate an employee; a deactivated Cashier/Server/Owner can no longer log in via `/api/login`, and a deactivated Kitchen employee's PIN is rejected by the clock endpoint -- both using the existing generic-rejection style, revealing no extra information.
- Owner can reactivate a previously deactivated employee, restoring their ability to log in or clock in.
- An Owner cannot deactivate their own account, nor the last remaining active Owner account -- both attempts are rejected with a clear error.
- Deactivating an employee never deletes or alters their historical `time_entries` or `orders` rows.
- An "Employees" section appears in `OwnerPage`'s navigation, consistent with the existing Table Layout / Menu Management sections, requiring no restructuring of the nav shell.
