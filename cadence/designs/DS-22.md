# C-22: Employee Management UI -- Design

## Parent
Part of [[EP-20]] -- see [[DS-20]] for the umbrella rationale. Depends on [[US-21]] (Employee Management API) landing first.

## Problem
Once [[US-21]] exists, the Owner still has no way to reach it -- there's no UI for registering, listing, editing, or deactivating employees.

## Approach
Add an "Employees" entry to `OwnerPage`'s `NAV_ENTRIES` data array ([[DS-16]]), alongside Table Layout and Menu Management, with a new nested route (e.g. `/owner/employees`) following the established `/owner/tables` / `/owner/menu` pattern. Build the section with antd `Table` (listing employees: name, role, active status) and `Form` (an "Add Employee" form with role-conditional fields -- password for Owner/Cashier/Server, PIN for Kitchen -- following the pattern established in [[DS-16]]'s MenuManager rebuild), `Card` for grouping, and `Switch`/`Button` actions for deactivate/reactivate and role/credential edit. Consumes [[US-21]]'s endpoints exclusively -- no direct database access from the frontend.

## Acceptance criteria
- An "Employees" entry appears in `OwnerPage`'s Sider/Menu navigation, without restructuring the existing Table Layout / Menu Management entries.
- A `Table` lists every employee with their name, role, and active/inactive status.
- An "Add Employee" `Form` lets the Owner create a new employee; selecting a role reveals the correct credential field (password for Owner/Cashier/Server, 6-digit PIN for Kitchen).
- The Owner can edit an existing employee's role and reset their credential.
- The Owner can deactivate and reactivate an employee from this screen; deactivating the Owner's own account or the last active Owner is blocked with a clear, visible error (surfacing [[US-21]]'s backend guard).
- All actions on this screen call [[US-21]]'s API endpoints; no employee data is read from or written to any other source.
