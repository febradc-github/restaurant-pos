# C-23: Owner Analytics Dashboard -- Design

## Problem

The Owner has no data-driven visibility into sales performance, which menu items are winning or losing, staff hours, or ingredient stock levels relative to what a day of service actually needs. [[EP-10]]'s C-13 story already built `GET /api/time-entries` specifically to feed this epic. No sales-aggregation or inventory-threshold logic exists anywhere in the codebase yet. This is the last piece of the original "digital transformation" goal.

## Architecture

Builds directly into [[EP-14]]'s `OwnerPage` nav shell ([[DS-16]]), which has already been extended twice without restructuring (Menu/Tables at launch, Employees in [[EP-20]]) -- a fourth "Analytics" entry follows the same pattern.

- **Sales/best-seller data**: new aggregation over `Order`/`OrderItem`/`MenuItem`, reusing the chainable-scope query pattern `TimeEntry` established (`forUser`/`forRole`/`clockedInBetween`) rather than one-off raw SQL, per the brainstorm panel's scout pitch. `Order` already has a real `paid_at` column (added in `2026_07_14_000010_add_payment_fields_to_orders_table.php`, set to `now()` by `PaymentConfirmationService` at checkout) -- confirmed against source during refine, correcting an earlier brainstorm assumption that only `created_at`/`updated_at` existed. Sales are dated by `paid_at`, filtered to `OrderStatus::Paid` only.
- **Inventory threshold/restock**: extends `InventoryItem` ([[EP-1]]/C-5) with a threshold column. Threshold is system-suggested from usage history (via the `menu_item_inventory_item` pivot's `quantity_required`, joined through `OrderItem`/`Order` filtered to Paid), not manually entered, though the Owner can override it. Computed live on each dashboard load -- no scheduled job, no stored snapshot history (unlike [[EP-10]]'s C-13 auto-close job, which this deliberately does not mirror).
- **Attendance**: consumes `GET /api/time-entries` ([[EP-10]]) directly -- no new backend work for this piece.
- **Frontend**: new "Analytics" `OwnerPage` nav entry and route, using the `dataviz` skill for chart design/color consistency with the established brand theme (`frontend/src/theme.ts`).

## Approach

Three stories:
1. **Sales & Best-Seller Analytics API** -- aggregation endpoint(s) over Paid orders (dated by `paid_at`): a sales-over-time series, and a best/worst-selling menu item ranking showing both quantity sold and revenue. Built with `Order`-model chainable scopes mirroring `TimeEntry`'s pattern.
2. **Inventory Threshold & Restock API** -- adds a threshold column to `InventoryItem`; a suggested-threshold computation from the trailing 30 days of Paid-order consumption (average daily usage per ingredient, derived via the `quantity_required` pivot); a live shortfall/restock endpoint (current stock vs. threshold, quantity needed per ingredient below threshold). A brand-new ingredient with no order history yet gets a suggested threshold of 0 (no shortfall shown) until usage accumulates; the Owner can override immediately regardless.
3. **Analytics Dashboard UI** -- new OwnerPage nav entry/route rendering charts for sales trend, best/worst-sellers (quantity + revenue), attendance/hours (from the existing C-13 endpoint), and the inventory restock list, using the `dataviz` skill for chart selection/styling.

## Trade-offs considered

- **Dating sales by `updated_at`** (the brainstorm's original assumption) -- rejected after verifying `Order` actually has a real `paid_at` column, set exactly once at checkout by `PaymentConfirmationService`. `paid_at` is semantically correct and immune to being touched by unrelated future changes to an order row.
- **A fully generic parameterized reporting endpoint** (`/api/reports/{metric}?group_by=...`), as the scout pitch floated -- rejected as over-engineering for the two chart types this epic actually needs today; the chainable-scope pattern is reused without committing to a generic query DSL.
- **Manually-set inventory thresholds** -- rejected in favor of system-suggested thresholds from usage history, per the user's explicit requirement that the system determine what's needed to serve one more day, not just record an Owner's guess. Owner override remains available.
- **Stored end-of-day inventory snapshot** (a scheduled job mirroring C-13's auto-close pattern) -- rejected for v1 in favor of a live, on-the-fly computation; no history table, no scheduled job. Historical restock-list tracking can be a future epic if needed.
- **7-day threshold window** -- rejected in favor of 30 days, trading some responsiveness to recent menu changes for less noise on low-volume ingredients.

## Acceptance criteria

- An "Analytics" section appears in `OwnerPage`'s navigation, without restructuring the existing Table Layout / Menu Management / Employees entries.
- A sales trend chart shows revenue over time, computed only from `Paid` orders, dated by `paid_at`.
- A best/worst-selling menu items view ranks items by both quantity sold and revenue over the covered period.
- An attendance/hours view is present, sourced entirely from the existing `GET /api/time-entries` endpoint.
- An inventory restock view shows, per ingredient: current stock, a system-suggested threshold (derived from the trailing 30 days of Paid-order consumption, defaulting to 0 for an ingredient with no order history), and the quantity needed to reach that threshold if currently below it.
- The Owner can override a suggested inventory threshold.
- Every chart/section on this dashboard is built using the `dataviz` skill's guidance for chart type and color choices, consistent with the existing brand theme.
- No new scheduled job or stored snapshot history is introduced for inventory data -- all inventory figures on this dashboard are computed live.
