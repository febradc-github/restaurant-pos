# C-10: Attendance & Extended RBAC -- Design

## Problem

The shipped POS (epic [[EP-1]]) deliberately made Server (waiter) and Kitchen device-level with no per-user login -- see [[AR-POS-core]], and [[SP-2]]'s explicit statement that "Server and Kitchen require no login and are not modeled as authenticated users at all." Only Owner and Cashier authenticate (built in C-2, login UI added in C-7).

The owner now needs time-in/time-out attendance tracking across all staff, driven roughly equally by payroll accuracy and shift/floor accountability. This requires reversing part of that architecture for Server, and adding a new lightweight identity mechanism for Kitchen that doesn't reintroduce a login gate on the kitchen order display.

## Architecture

This epic bends the "Server/Kitchen: no login" decision recorded in [[AR-POS-core]] and [[SP-2]]. It does not fully reverse it:

- **Server**: gains a real login, following the exact pattern Cashier already uses ([[app-http-controllers-api-authcontroller-php]], Sanctum bearer tokens per [[adr-007-sanctum-bearer-tokens]]). Server becomes a normal authenticated `UserRole::Server` account.
- **Cashier**: existing login/logout ([[src-api-auth-ts]], [[src-components-login-tsx]]) is retrofitted to also write a `time_entries` row -- no new UI, only a side effect added to the existing flow.
- **Kitchen**: the order display ([[src-app-tsx]] routing to the no-auth kitchen view) stays public and gate-free -- that constraint from [[AR-POS-core]] is preserved deliberately, since slowing down kitchen order visibility was the reason Server/Kitchen were no-login in the first place. Kitchen staff become real `UserRole::Kitchen` User records, but authenticate for clock-in/out purposes only, via a separate lightweight 6-digit PIN endpoint (not Sanctum email/password login, not `auth:sanctum` middleware on the order display route).
- **New**: a `time_entries` table/model (`user_id`, `role` snapshot, `clock_in`, `clock_out` nullable, `auto_closed` boolean) and a scheduled job that closes any entry still open past a configurable daily cutoff, flagging it `auto_closed` for the Owner to review.

This is foundational for two not-yet-refined epics from the same brainstorm session: Owner employee management (registers the User/role records this epic authenticates against) and the Owner analytics dashboard (surfaces `time_entries` as attendance/hours data). A brain-curator dispatch after approval will record the superseding decision against [[AR-POS-core]] and [[SP-2]] so the "no login" architecture note reflects this change rather than going stale.

## Approach

1. Extend `UserRole`-gated Sanctum auth (already built for Owner/Cashier) to Server: same login/logout endpoints, same frontend `Login.tsx` flow, gated to the Take-Orders page.
2. Add `time_entries` migration + model. Hook Cashier's and Server's existing/new login action to create a row (`clock_in = now()`), and logout action to set `clock_out = now()` on the user's open row.
3. Add a Kitchen-specific PIN clock-in/out endpoint: accepts a 6-digit PIN, resolves it to a `UserRole::Kitchen` User (PINs unique among active Kitchen staff), writes/closes a `time_entries` row. No Sanctum token issued -- this is attendance-only, not a session grant. The kitchen order display route remains unauthenticated and unaffected.
4. Add a scheduled job (Laravel scheduler) that runs at a configurable daily cutoff and closes any `time_entries` row still open, setting `auto_closed = true`.
5. Frontend: add a PIN-pad overlay component on the Kitchen display page for clock-in/out, and wire Server's Take-Orders page behind the existing `Login`/session pattern Cashier already uses.

## Trade-offs considered

- **Lightweight Employee record instead of real User accounts for Server/Kitchen** -- rejected. Reusing the existing Sanctum/`UserRole` infrastructure is simpler than building and maintaining a second, parallel identity model, and Server needs full authentication anyway per the brainstorm decision.
- **Leaving forgotten clock-outs open indefinitely** -- rejected in favor of an auto-close job at a configurable daily cutoff, since indefinitely-open entries would corrupt the payroll/hours data this epic exists to produce. The Owner can still review and correct `auto_closed` entries.
- **Gating the Kitchen order display itself behind login** -- rejected; preserves the deliberate C-1 decision that kitchen order visibility must not be slowed down by a login step. The PIN clock-in is a separate, optional overlay, not a route guard.

## Acceptance criteria

- Server can log in and log out through the same auth pattern Cashier uses; login creates a `time_entries` row (`clock_in`), logout sets `clock_out` on that row.
- Cashier's existing login/logout is retrofitted to also create/close a `time_entries` row, with no change to its existing auth behavior.
- The Kitchen order display remains reachable with no login required, unchanged from today.
- A separate PIN-pad clock-in/out overlay on the Kitchen display lets a Kitchen employee, identified by a unique 6-digit PIN, create/close their own `time_entries` row without a Sanctum session being issued.
- Server and Kitchen staff exist as real `User` records with `UserRole::Server` / `UserRole::Kitchen`, enabling standard role-gated API access for future work.
- Any `time_entries` row left open past a configurable daily cutoff is automatically closed by a scheduled job and flagged `auto_closed`.
- `time_entries` rows are queryable by user, role, and date range (supports the future Owner analytics epic).
