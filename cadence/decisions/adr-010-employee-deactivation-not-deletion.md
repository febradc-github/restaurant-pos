# ADR-010: Employee Deactivation Instead of Hard Delete

## Context

C-20 (Owner Employee Management, [[EP-20]]) introduces the first real, in-app employee registration flow for this POS. Owners can now create employees with name, role, and role-appropriate credentials (password for Owner/Cashier/Server, 6-digit PIN for Kitchen), and must also be able to remove or transition employees from the roster.

The question: when an employee leaves, should their User record be hard-deleted from the database, or deactivated (soft-delete via an `active` boolean flag)?

Hard deletion would orphan or cascade-delete related rows:
- `time_entries` records (from [[EP-10]] "Attendance & Extended RBAC") -- attendance history needed for payroll reconciliation, shift accountability, and owner reporting.
- `orders` rows linking to that `user_id` (Server who took the order, Cashier who confirmed payment) -- order history needed for sales reports and dispute resolution.

The restaurant needs historical data to remain intact for compliance, auditing, and business analytics. Deleting a User would destroy the audit trail and make payroll/reporting unreliable.

## Decision

**Employees are deactivated, never hard-deleted.**

An `active` boolean column (default `true`) is added to the `users` table. When an Owner removes an employee, `active` is set to `false`.

Login checks are extended to also verify `active`:
- **AuthController::login** (used by Owner/Cashier/Server): rejects login attempts by inactive users with the generic "invalid credentials" error already established in C-11/C-12, preserving the error-message style.
- **KitchenClockController::clock** (PIN-based clock-in/out endpoint for Kitchen staff): also rejects inactive users with the same generic error.

A deactivated employee can be reactivated later (e.g., seasonal staff returning or a mistake corrected) by setting `active = true` again.

### Self-Lockout Guard

The system enforces two safety checks to prevent an unrecoverable "nobody can log in" state:
1. **An Owner cannot deactivate their own account.** The request is rejected with a clear error message ("Cannot deactivate your own account").
2. **An Owner cannot deactivate the last remaining active Owner account.** If only one Owner has `active = true`, attempting to deactivate that account is rejected with a clear error ("Cannot deactivate the last active Owner account").

These guards apply only to deactivation requests from OwnerPage's employee-management UI; the system does not prevent editing the `active` column directly via database (that's acceptable administrative power).

## Owner-Set Credentials

As part of C-20, credentials are Owner-set directly within the app, not system-generated and delivered:
- Passwords (for Owner/Cashier/Server) are entered by the Owner in the employee creation form.
- PINs (for Kitchen) are entered or generated by the Owner in the employee creation form.

This choice is deliberate: this project has no email/SMS delivery infrastructure, and the use case (single-location restaurant) allows the Owner to relay credentials directly to staff in person or via their preferred channel. Avoiding a credential-delivery system simplifies the MVP.

## Alternatives Considered

1. **Hard delete employees with cascade/null-foreign-key:** Rejected because it destroys historical `time_entries` and `orders` data, breaking payroll and sales reporting. The Owner needs audit trails.

2. **Separate "Employee" model from "User":** Rejected because reusing the existing `User` / `UserRole` infrastructure is simpler. Employees are already Users (with roles); adding a parallel Employee table would duplicate identity logic.

3. **Archived/Disabled flag separate from User (e.g., on an Employee row):** Rejected because login gating must happen at the `User` level in AuthController and KitchenClockController. Having the flag elsewhere complicates middleware and adds indirection.

4. **System-generated credentials with email/SMS delivery:** Rejected because this project has no delivery infrastructure. Introducing one would delay C-20 and add operational complexity (SMTP/SMS credentials, retry logic, template management). Direct Owner-set credentials fit the restaurant workflow.

## Consequences

- **Pro:** Historical `time_entries` and `orders` data remains intact and queryable for payroll, reporting, and compliance.
- **Pro:** Deactivated employees can be reactivated without re-creating User records or losing history.
- **Pro:** Self-lockout guards prevent operational emergencies ("nobody can log in").
- **Pro:** Login-gating logic is simple and co-located with existing auth middleware.
- **Con:** `users` table includes inactive rows; queries must filter `active = true` to reflect current roster (mitigated by Owner-facing reporting queries already applying this filter).
- **Con:** No soft-delete audit trail for who deactivated an employee or when (future enhancement: add `deactivated_at` and `deactivated_by_user_id` timestamps if auditing becomes a requirement).
